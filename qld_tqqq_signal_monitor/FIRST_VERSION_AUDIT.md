# 第一版运行审计

审计对象：`48da8054013d66b5951e91d601db17a49b03c76a`，提交说明为 `Add weekday QLD/TQQQ signal notifications`。

## 结论

第一版的**策略数学和时间顺序正确**：

- 使用 QQQ 收盘价计算 50/200、55/220、60/240 三组 SMA/EMA 趋势状态。
- 每组在 SMA 或 EMA 任一看多时计为开启，三组平均形成趋势分数。
- 使用截至信号日的 21 个 NDX 对数日收益计算样本标准差，并乘以 `sqrt(252)` 年化。
- 使用 60% 目标波动率计算 QLD 和 TQQQ 目标权重。
- 仅把每月最后一个交易日的收盘数据作为新信号。
- 新目标在下一交易日执行，因此没有用月末收盘信息回填同日交易。
- 非月末继续使用最近一次月末目标，没有日度再平衡规则。

第一版的**运行实现并不完全正确，因此不应把 `main` 强制回退到该提交**。

## 第一版存在的操作层问题

### 1. QQQ 历史请求不稳定

第一版使用 Yahoo `range=max` 请求。首次端到端部署只返回了不完整历史，因此安全校验拒绝生成信号。后续版本改为显式 `period1` 和 `period2`，才稳定取得完整 QQQ 历史。

### 2. 交易日历起点可能越界

第一版直接把数据最早日期传给 `exchange_calendars`。当数据早于已安装日历版本的首个可用 session 时会报错。后续版本把查询起点限制到 `calendar.first_session`。

### 3. 固定 UTC 时间会随夏令时偏移

第一版使用 `05:30 UTC`。该时间在夏令时和标准时对应不同的太平洋本地时间。当前工作流明确使用 `22:30 America/Los_Angeles`。

### 4. “上期目标”曾被误写成“当前账户权重”

第一版只能知道上一次月末模型目标，不能知道账户经过一个月价格漂移后的真实权重。把两个目标的差直接展示为实际交易变化会误导执行。当前版本明确要求在下一交易日开盘，从实际账户持仓再平衡到本期目标。

### 5. 第一版正常结果每天发布

第一版工作流在每个交易日都向 issue 发布一次成功结果。策略本身虽然没有每日调仓，但通知频率容易被误解为每日更新。当前版本仍按工作日运行日历和数据检查，但只有开放市场的月末交易日满足 `publish_notification=true`，因此正常 issue 更新严格为月度。

## 当前保留的规范

当前 `main` 应保持以下单一执行合同：

1. 工作日自动检查，用交易日历识别真实月末。
2. 非月末不发布成功通知，不产生交易指令。
3. 月末收盘后计算新目标。
4. 下一交易日开盘，从实际账户权重再平衡到新目标。
5. 月内允许持仓自然漂移，不做日度或周度重平衡。
6. 数据校验失败时 fail closed，不使用陈旧价格、代理价格或猜测值。
7. QLD 与 TQQQ 是替代方案，不能叠加。

因此，正确处理方式是保留后续修复并收紧为月度发布，而不是回退到第一版代码。

# QLD / TQQQ 月度信号通知

该程序执行已经冻结的月度趋势与波动率策略，并把月末目标发布到仓库 issue #1。程序只生成通知，不连接券商，也不自动下单。

GitHub Actions 为了可靠识别“每月最后一个美国股票交易日”，采用每小时调度机会，在Pacific晚间及次日开盘前检查日历和数据。**正式目标仍只来自月末收盘；允许在下一交易日开盘前补发，不增加月内调仓。** 数据校验失败仍会发布安全警报并拒绝产生交易指令。issue #1 还维护一条持续更新的自动运行状态心跳，用来区分“任务未运行”和“任务已运行但非月末”。

## 固定策略

- 趋势输入：QQQ 价格收盘序列。对当前实盘时期，QQQ 与回测连续信号序列仅相差固定比例，因此均线状态一致。
- 三组趋势参数：50/200、55/220、60/240。
- 每组中 SMA 或 EMA 任一快线高于慢线，该子模型即开启。
- 趋势分数：开启子模型数除以 3。
- 风险输入：NASDAQ-100 最近 21 个交易日的年化已实现波动率。
- 目标波动率：60%。
- QLD 权重：`score × min(2, 0.60 / vol) / 2`。
- TQQQ 权重：`score × min(3, 0.60 / vol) / 3`。
- 剩余仓位：短期美国国债或现金。
- 仅在每月最后一个交易日收盘后生成新目标。
- 新目标在下一交易日开盘执行。
- 月内不做重新平衡，也没有暴跌日应急减仓。

QLD 和 TQQQ 是两种替代实施方案，不能把两行权重同时叠加。

## 月末通知如何执行

模型在月末给出目标权重。账户内的 QLD/TQQQ 与防御资产会在月内自然漂移，因此“上期月末目标”不是月末当天的实际账户权重。

精确执行方式是：

1. 使用月末收盘数据计算“本期目标”。
2. 在下一交易日开盘，以实际账户持仓为起点再平衡到该目标。
3. 非月末不交易，继续持有月内自然漂移后的组合。

系统不读取券商账户，因此不会把两个模型目标之差误写成实际买卖数量。具体买入或卖出方向取决于账户当时的真实权重。

## 暴跌日与执行边界

该回测策略没有盘中止损、单日跌幅阈值、VIX 应急开关或非月末调仓规则。

- 非月末发生大跌时不产生交易指令。
- 月末发生大跌时，使用该月末收盘数据生成新目标，并在下一交易日开盘执行。
- 任何依赖当日收盘价的信号都不能在同一交易日收盘前执行。
- 增加“暴跌后立即减仓”会形成另一套策略，必须重新进行 1985–2026、QLD 实际期和 TQQQ 实际期回测。

## 第一版审计结论

最初部署提交 `48da805` 的核心公式、月末信号频率和下一交易日执行原则是正确的，但第一版的运行实现并不适合直接回退。后续提交修复了 QQQ 历史数据不完整、交易日历起点越界、固定 UTC 调度的夏令时偏移，以及把“上期月末目标”误标为账户当前权重的问题。

原始版本审计见 [`FIRST_VERSION_AUDIT.md`](FIRST_VERSION_AUDIT.md)，最新故障与修复见 [`OPERATIONS_REPAIR.md`](OPERATIONS_REPAIR.md)。当前版本保留这些修复，并将正常的 issue 发布严格限制为月末更新。

## 数据与安全控制

- QQQ：Yahoo Finance chart endpoint 的价格收盘字段。程序不使用含现金分配调整的 `adjclose`。
- NASDAQ-100：FRED `NASDAQ100` 日收盘序列。
- 两个数据源都必须包含报告日，并通过长度、重复日期、正价格和最近 60 日收益相关性检查。
- 数据缺失、过期、格式变化或交叉校验失败时，程序拒绝产生交易指令。
- Python 直接依赖锁定到完成端到端验证的版本；GitHub Actions 固定到已发布 commit。

## 自动运行与恢复（2026-09-04修复）

工作流改为显式 UTC cron `7 * * * *`。因为美国时区偏移为整数小时，这相当于每个 Pacific 小时的 :07 获得一次调度机会。仅实际运行时处于 **18:00至次日06:59 PT** 的定时任务进行取数；名义取数检查为18:07、19:07……次日06:07。其他小时仅完成时间窗判断。周末、节假日保留补跑机会，交易日由XNYS日历决定。

GitHub cron没有准时或必达保证。小时级重试降低漏掉单次调度的影响，并不构成服务等级保证。`repository_dispatch` 的 `qld-tqqq-check` 接口已预留给独立调度器，但**当前没有配置外部调度服务**。

程序先选最近已完成且经过30分钟缓冲的真实交易日，再要求QQQ和NDX都存在该日收盘。不会将普通日历“昨天”当成交易日。Yahoo历史接口返回HTTP 200但日期陈旧时，尝试90天近期日线，检查重叠收盘一致后刷新；失败再换另一Yahoo端点。FRED也检查完整日期及近期请求。跨源相关性检查保持不变，最近260个交易日的缺口会拒绝通过。没有使用盘中报价、调整后价格、QQQ推算NDX、前向填充或未知代理。

网络和日期新鲜度失败均最多进行3轮数据重试，轮间等待20秒、60秒。每轮来源、最后数据日和失败原因写入`status.json`；已验证近期收盘写入`verified_closes.csv`。Actions保存审计产物30天。

issue #1只在月末发布正式交易目标，每次检查更新同一条心跳，列明数据源、实际收盘日期及价格。报错后恢复会编辑原错误评论，标记“已恢复”并保留原诊断。心跳只代表所注明时间的最近一次核验，**不表示准时或持续在线**。

月末收盘信号可在跨午夜、周末或假期后补发，但最晚必须在下一交易日开盘前10分钟完成发布，即通常06:20 PT。超过截止且没有成功通知时，发布漏报报警；不补做已过期交易，不把历史信号改成当日订单。正常月度规则和模型公式完全不变。

手动设置`report_date`仅作历史复算：保存报告和审计文件，不发布交易通知，也不覆盖生产心跳。`push`及未指定日期的手动运行使用与正式任务相同的实时校验。

## 本地运行

```bash
python -m pip install -r qld_tqqq_signal_monitor/requirements.txt
python qld_tqqq_signal_monitor/exact_monitor.py
```

指定历史报告日：

```bash
python qld_tqqq_signal_monitor/exact_monitor.py --report-date 2026-08-31
```

输出写入 `signal_output/report.md` 与 `signal_output/signal.json`。结构化输出中的 `publish_notification` 必须同时满足真实月末信号、实时模式以及未超过次日开盘前10分钟的通知截止时间。
